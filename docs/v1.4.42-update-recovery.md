# v1.4.42 自动更新接管修复

## 根因
旧版 Host 在启动独立 PowerShell 更新器之前就将状态写成 `applying`，且没有更新器的启动握手、早期 stdout/stderr 记录与接管超时检测。单独的 Powershell 解析/启动失败会使 UI 长时间停留在“正在替换程序并重启”，即使文件并未被更改。仅凭截图不能确定是否还有其它 Windows 环境故障。

## 更改
- 更新器复制到 `data/updates/` 后独立运行，避免它自身所在 `scripts/` 被替换。
- 分离 `handoff`、`preparing`、`stopping`、`backing_up`、`applying`、`restarting`、`failed`、`rolled_back`、`success`，每一阶段写入状态文件；接管 90 秒未确认，页面提示检查日志。
- 记录 `updater-bootstrap.log`（PowerShell 解释器启动级输出）与 `updater.log`（脚本执行状态），管理员后台提供“查看更新日志”。
- 保留 GitHub Release ZIP/SHA-256 校验、VM 任务保护、数据库/凭据/虚拟机目录不覆盖以及失败回滚。
- 单独提供 `Repair-Stuck-Update.cmd/.ps1`，用于 v1.4.39/1.4.40 更新系统已卡死时手动修复，不需要修改或删除运行数据库。

## 修复卡住的旧系统
从 GitHub v1.4.42 Release 下载 `VM-Orchestrator-v1.4.42.zip` 和同名 `.sha256`，与本次提供的 `Repair-Stuck-Update.cmd` 和 `.ps1` 放在同一文件夹。确认 `Repair-Stuck-Update.cmd` 中 `VMO_TARGET` 为现有 VMO 安装根目录，在**运行 VMware Workstation 的 Windows 用户账户**下执行这个 CMD（该用户要拥有安装目录的修改权限）。先停止新 VM 任务，脚本验证并解压 ZIP、检查 8765 是否属于 VMO、备份代码、替换，进行健康检查；失败时尝试回滚。

诊断文件：`<安装根目录>\data\updates\status.json`、`updater.log`、`updater-bootstrap.log`。不要删除 `data/` 或 Windows 用户的 DPAPI 密钥。

## 验证边界
Linux 容器只能测试 Python/JS/打包；Windows PowerShell 5.1、VMware Workstation、独立进程停止与恢复必须在目标 Windows 用户会话中实际验证。


## Windows PowerShell 5.1 encoding compatibility

The v1.4.42 detached updater and one-time recovery runner use ASCII-safe
PowerShell source, so scripts remain parseable regardless of Windows ANSI code page.
The recovery tool also normalizes extracted updater scripts to UTF-8 with BOM.
For older versions, script parse errors (UnexpectedToken) must be corrected before retrying;
no code replacement takes place when PowerShell fails parsing the script.
